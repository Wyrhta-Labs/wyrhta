# 0010 — `@wyrhta/core` stays a git dependency that builds on install

**Status:** accepted 2026-08-19 · **Supersedes nothing.** Records the outcome of
an investigation into npm 11's install-script policy, whose starting premise
turned out to be wrong.

## Context

Both consumers pin the shared library as a **git tag**
(`"@wyrhta/core": "github:Wyrhta-Labs/wyrhta-core#v0.3.0"`), per the
three-independent-repos arrangement in `AGENTS.md`. core's `dist/` is
git-ignored, and its `prepare` script (`npm run build` → `tsc`) compiles it at
install time.

npm 11 gates install-time lifecycle scripts behind an `allowScripts` policy, and
this was believed to threaten that arrangement. The reported symptom was a
warning naming core specifically —
`npm warn allow-scripts @wyrhta/core@0.3.0 (prepare: npm run build)` — with the
inference that a runner enforcing the policy strictly would install core
**unbuilt**, so the service would fail late at import rather than at install.

Three fixes were on the table: allowlist the script; ship `dist/` in the release
tag; or move core to a real package registry.

**The premise did not survive measurement.** On npm 11.17.0 / Node v26.5.0:

- The `allow-scripts` warning **does not name core at all.** It names `esbuild`
  (×4), `argon2` (`node-gyp`) and `fsevents` (×2) — third-party packages with
  genuine native install scripts. Verified on a cold path: core's packed-tarball
  cache entry deleted, `node_modules` removed, `npm ci` re-run. npm's own debug
  log shows the nested clone-and-build really executed, and no core line was
  emitted. Fifteen retained npm debug logs contain zero hits for
  `allow-scripts.*wyrhta`.
- **Why:** on a lockfile-driven install `node.package.scripts` is empty, and
  arborist's disk-read fallback only fires when `hasInstallScript === true`.
  core's `package-lock.json` entry carries no such flag, so its `prepare` is
  never enumerated.
- **An `allowScripts` entry for core is therefore not load-bearing.** Proven by
  counterfactual: with the key set to `false` (an explicit *deny*) and the cache
  busted, `npm ci` exited 0 and `dist/index.js` was still built. core's `prepare`
  runs at pacote **pack** time inside the git clone, which does not consult
  `allowScripts` at all.
- `--strict-allow-scripts` **fails the install hard** rather than installing
  something broken — so the feared silent-unbuilt install is not what strict mode
  produces. It fails identically with and without a core entry, because the seven
  packages it objects to are the third-party ones.
- The real silent-breakage path is **`--ignore-scripts`**, which overrides
  `allowScripts` entirely. Verified: exit 0, no warning at all,
  `node_modules/@wyrhta/core/` containing only `README.md` and `package.json`,
  and `ERR_MODULE_NOT_FOUND` on first import.
- **Container builds are safe.** A `docker build --no-cache` of KithLedger — a
  genuinely empty npm cache — completed with exit 0, and the resulting image
  contains `node_modules/@wyrhta/core/dist/index.js` with a successful dynamic
  import. Neither Dockerfile passes `--ignore-scripts` or
  `--strict-allow-scripts`.

## Decision

**Keep core as a git dependency that builds on install.** The arrangement is not
broken; there was materially less to fix than the symptom suggested. Three things
change instead.

### 1. Record the approval, in both consumers

Each consumer's `package.json` carries an `allowScripts` entry for core,
generated by `npm approve-scripts @wyrhta/core` rather than hand-written:

```json
"allowScripts": {
  "github:Wyrhta-Labs/wyrhta-core#87618273a8effe61f30668fb4d3a197f74a639cd": true
}
```

It is kept **despite being a no-op today**, because the reason core escapes the
gate is an npm implementation detail (`hasInstallScript` absent from the lockfile
entry), not a guarantee. If a future lockfile regeneration sets that flag, core
becomes gated and the entry starts doing real work — in both consumers at once.
Cheap insurance against a fragile internal.

**Note the maintenance cost:** the key pins the resolved **40-char SHA**, not the
tag. A key written with `#v0.3.0` silently fails to match, because the lockfile
stores the SHA and matching requires the key's committish to be a *prefix* of it.
So bumping the core pin means updating the `allowScripts` key too, in both
consumers.

### 2. `--ignore-scripts` is unsupported against this dependency

Now written down rather than discovered. There is no cheap guard: a consumer-side
`postinstall` assertion would itself be skipped by the same flag. Any CI or image
build that hardens installs this way must instead satisfy core from a prebuilt
source.

### 3. The third-party scripts stay unreviewed, deliberately

Silencing the real warning means approving four `esbuild` postinstalls, `argon2`'s
`node-gyp rebuild` and two `fsevents` installs. That is a decision about running
third-party native build scripts on the household server, and it is the
maintainer's to make explicitly — not something to fold into an unrelated build
commit.

### Options considered and not taken

- **Ship `dist/` in the release tag.** Would remove the script entirely, making
  `--ignore-scripts` safe and skipping the nested devDependency install at pack
  time. Rejected for now: it puts build output in git, and core's release
  convention has every tag sitting on a commit present on **both** `staging` and
  `main`, which committed artifacts complicate. Nothing currently forces it.
- **Move core to a package registry.** The clean long-term answer — a published
  tarball needs no build step at install. Rejected for now on cost: GitHub
  Packages requires authentication even for public reads, so both Dockerfiles
  would need a build secret, and core is deliberately a public repo.

**Revisit either option when any of these becomes true:** a CI runner or image
build genuinely needs `--ignore-scripts`; a third consumer appears (the
per-consumer `allowScripts` bookkeeping stops being trivial at three); or npm
starts gating core's `prepare` for real, at which point the entry becomes
load-bearing and the pin-bump churn becomes a real cost rather than a theoretical
one.

## Consequences

**Easier.** No change to core's release process, no build artifacts in git, no
registry auth in the Docker builds. The install-script policy for both consumers
is now explicit and reviewable in-repo.

**Costs.** Bumping the core pin is a two-line change per consumer, not one, and
forgetting the second line is silent — the entry simply stops matching, and today
nothing breaks, which is exactly what makes it easy to miss.

The real `allow-scripts` warning stays on screen at every install until the
third-party scripts are reviewed. That noise is the price of not rubber-stamping
them.

**Known and out of scope.** On the Windows development host, an install against a
genuinely empty **global** npm cache fails inside core's git clone with
`spawnSync … esbuild.exe ENOENT`, from esbuild 0.18.20's `install.js` in core's
own devDependency tree — most likely the long `_cacache/tmp/git-clone*` path.
Container builds are unaffected (proven above), so this is a local-toolchain
problem, not a deployment one.
